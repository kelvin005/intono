# ADR 0010: iOS app architecture for Phase 2 (AVAudioEngine shim, Simulator-only CI, TestFlight before launch)

Status: **Proposed** (2026-11-27). Needs Kelechi's answers to the questions at the end, then "merge". Amendments by ADR only.

## Context

ADR 0009 built the Android app: the C API (`intono.h`, unchanged), a portable C++ core in the shim (`AudioPump`, the bench, the soak),
a thin Oboe layer, Kotlin glue behind the method channel `intono/audio`, and one Flutter UI that reads the engine over `dart:ffi`.
Its consequences say iOS repeats decisions 3 to 5 with Apple's audio APIs, in its own ADR. This is that ADR.

**Testing decision (Kelechi, 2026-11-27):** the iOS shim is built on AVAudioEngine and tested **on the iOS Simulator in CI only**.
Testing on a real iPhone moves to **just before the iOS launch, through TestFlight**. Until then, no iPhone is available to the project,
and no iOS number comes from a real device.

Constraints:
- The Claude workspace has no Xcode; iOS is verified by CI on `macos-15` (pinned) only.
- The Simulator runs the Mac's CPU and the Mac's (or no) audio hardware. Its timings say nothing about an iPhone, and on a CI runner it
  may have no microphone. Tests are written for that.
- No new vendors or services without an ADR. TestFlight needs the Apple Developer Program (a paid account and an App Store Connect
  record): a new vendor, decided here only as "before the iOS launch" (question 3).

## Decisions

### 1. Layout

```
dsp/                        libintono (unchanged); dsp.yml already builds intono.xcframework (device + simulator slices)
android/shim/src/           portable C++ core, shared: audio_pump.*, bench.*, soak.* (no Android or Apple headers)
ios/shim/                   Objective-C++: AVAudioEngine session + C glue for Swift (links libintono and the portable core)
app/ios/                    Flutter's iOS host (Runner, Swift glue for the method channel, XCTest smoke tests)
```

The portable core stays where it is and the iOS build compiles the same files (question 2). Nothing in Swift or Dart is on the audio path.

### 2. Audio shim: AVAudioEngine with real-time nodes

```
 mic ──► AVAudioEngine.inputNode ──► AVAudioSinkNode ──(RT block)──► AudioPump.on_input ──► intono_process
                                                                                        └──► frames/notes rings ──► Dart (vsync)
 AVAudioSourceNode ◄──(RT block)── AudioPump.on_output ◄── intono_drone_render ──► mainMixerNode ──► output
```

- **Capture through `AVAudioSinkNode`** (iOS 13+), whose block runs on the real-time render thread with the hardware buffer. Not
  `installTap(onBus:)`: a tap is delivered off the real-time thread, in large and variable buffers, which defeats the hop timing.
- **Drone through `AVAudioSourceNode`** (iOS 13+) into the main mixer; started only while the drone plays, like the Android output stream.
- **AVAudioSession:** category `.playAndRecord`, mode `.measurement` (the system's voice processing, AGC and EQ off: the counterpart of
  Oboe's `Unprocessed` preset), options `.allowBluetoothA2DP` and `.defaultToSpeaker`, preferred IO buffer 5 ms (about 256 frames at 48 kHz:
  the granted value is reported, never assumed), preferred sample rate = the hardware rate. The engine is created at the granted rate.
- **The same `AudioPump`** as Android (block sizes, timing stats, gaps by sample time, drone path, RT-safety: no allocation or lock in the
  blocks). Its host tests already run on Linux; they are added on macOS in the iOS job.
- **Interruptions and route changes** (call, Siri, headphones unplugged): observed in the shim. Capture stops on an interruption and is
  reported as a plain state, as on Android. Headphones: `AVAudioSession.currentRoute` outputs (headphones, Bluetooth A2DP/HFP/LE, USB) with
  the route-change notification. Same drone policy as ADR 0009 decision 4 (off unless headphones; speaker warning).
- iOS deployment target **13.0** (as the xcframework job; `AVAudioSinkNode` needs 13).

### 3. Flutter host and FFI

- `app/ios` is generated by the pinned Flutter (`app/.flutter-version`), Swift, no CocoaPods dependency beyond Flutter's own.
- libintono and the shim are **linked statically** into the Runner; Dart opens them with `DynamicLibrary.process()` on iOS (Android keeps
  `DynamicLibrary.open('libintono_android.so')`). The eight `intono_*` functions and `intono_bench_run` are kept from dead-stripping
  (one `-Wl,-u,_<symbol>` linker flag per symbol), and CI checks that the Runner binary contains them.
- **The same method channel `intono/audio`** and the same calls as Kotlin (start, stop, enginePointer, setDrone, headphones, info,
  lastError, startSoak, soakStatus, finishSoak), so the Dart UI, its tests and `AudioControl` are unchanged.
- Microphone permission through `AVAudioApplication.requestRecordPermission` (iOS 17+) or `AVAudioSession.requestRecordPermission`
  (13 to 16), with `NSMicrophoneUsageDescription` in `Info.plist`.
- Bench mode is the same screen. The denormal-guard comparison (a guard-OFF build of libintono) is not built for iOS in Phase 2: on the
  Simulator its timing says nothing about an iPhone, and the comparison is information already taken on the Android phone. It can be added
  as an embedded framework for the TestFlight milestone if wanted.

### 4. CI (Simulator only, no signing)

A new job `ios-app` in `flutter-app.yml` on `macos-15`:

1. Shim host tests (`AudioPump`, bench, soak) on macOS arm64 (plain build).
2. `flutter build ios --simulator --no-codesign` (Debug) for the arm64 Simulator.
3. Checks: the Runner binary contains the `intono_*` symbols; `NSMicrophoneUsageDescription` is set; deployment target 13.0.
4. **XCTest on a booted Simulator** (a pinned runtime and device type, recorded in the implementation PR from what `macos-15` ships):
   library and engine smoke test (create, process a generated tone, read frames and notes, destroy) through the same C API Dart uses;
   the `AVAudioSession` configuration is applied and its granted values logged; the shim starts and stops cleanly **or** reports
   "no input device" as a plain error, never crashes (the runner may have no audio input). Capture itself is not asserted on CI.
5. `flutter test` already runs on Linux for the Dart side; it is not repeated on macOS.

No signing identity, provisioning profile or Apple account is used in CI. No IPA is produced.

### 5. Real iPhone: TestFlight, just before the iOS launch

- Real-device testing (latency, worst hop, soak, battery, the live meter by ear) happens in a pre-launch milestone through TestFlight,
  with a signed build. Until then the iOS app is accepted on Simulator evidence only.
- **No device caps for iOS come from the Simulator.** The ADR 0008 measurements (worst hop, W3, W4, polling power) are repeated on the
  iPhone in that milestone, and the iOS caps are set by an amendment of this ADR from them.
- What TestFlight needs (Apple Developer Program, App Store Connect record, bundle id = the final app id, signing in CI or locally) is
  decided in that milestone's ADR. The final app id is already due before Phase 5 (ADR 0009 answer 3).

### 6. Milestones

- `phase2-android-complete`: as in ADR 0009 (phone measurements and the device-cap amendment).
- `phase2-ios-sim-complete`: PRs i1 to i3 merged with the `ios-app` job green (build, symbol checks, XCTest smoke on the Simulator).
- iOS device acceptance: the pre-launch TestFlight milestone, not Phase 2.

## PR sequence (tests first, CI green; i2 and i3 may be merged by Claude under the standing rule once this ADR is accepted)

- **i1** this ADR (proposed) and the Phase 2 plan entry.
- **i2** `ios/shim` (AVAudioEngine session, sink and source nodes, session configuration, interruptions, route/headphones) + C glue, with
  the portable core's host tests on macOS; `flutter create`-generated `app/ios` with the Swift method-channel glue; `DynamicLibrary.process()`
  on iOS; the `ios-app` job (build and checks).
- **i3** XCTest smoke tests on the Simulator in `ios-app`; bench and soak screens on iOS (guard ON only; Simulator numbers are information only).

## Questions for Kelechi

1. **Simulator-only acceptance:** the iOS part of Phase 2 closes on Simulator evidence (`phase2-ios-sim-complete`), and every
   iOS device number, including the iOS caps for the audio thread, waits for the TestFlight milestone. Agreed?
2. **Shared native code:** the iOS build compiles the portable core in place from `android/shim/src/` (no move, no churn). The alternative
   is to move `audio_pump`, `bench` and `soak` to a neutral `native/` directory now. Recommendation: in place now; move only if a third
   platform appears.
3. **Apple Developer Program:** needed for TestFlight. Enrol only when the pre-launch milestone starts (recommended), or earlier?

## Consequences

- No new dependency in i2 and i3 beyond Apple's SDK and Flutter's iOS tooling; the Apple Developer Program is deferred to the TestFlight
  milestone.
- `intono.h`, `openapi.yaml`, the gates and the thresholds do not change.
- Until TestFlight, iOS latency, timing and battery are unknown; the Simulator proves building, linking, the C API on iOS, the session
  configuration and that the shim does not crash.
