# ADR 0009: Android app architecture for Phase 2 (audio shim, Flutter FFI, bench mode, CI)

Status: **Accepted** (Kelechi, 2026-11-23: PR #3 merged, open questions answered below). Amendments by ADR only.

## Context

Phase 1 delivered `libintono` (C API in `intono.h`, ADR 0003/0008): `intono_process` on the audio thread, `intono_drone_render` on the audio thread, `intono_read_frames` and `intono_read_notes` on the UI thread. The C API does not change in Phase 2 unless an ADR says so; none of the decisions below needs a change.

Phase 2 builds the Android app: low-latency microphone capture and drone playback, a Flutter UI reading the engine through `dart:ffi`, a live meter (note, cents, needle), and an on-device bench mode. iOS follows Android with the same structure (separate ADR).

Constraints that shape the decisions:
- The Claude workspace has no Android SDK, no Flutter and no general internet access. Android and Flutter builds can only be verified by CI, and anything involving a microphone or real latency only on Kelechi's phone. The headless CI emulator (`-no-audio`) cannot test capture.
- No new vendors or services without an ADR. ADR 0005 already ruled out third-party GitHub Actions without an ADR.
- No audio is ever logged, stored or uploaded. The bench report contains only timing numbers.

## Decisions

### 1. Layout

```
dsp/                       libintono (unchanged)
android/                   Android-only code
  shim/                    C++: audio pump + Oboe streams + JNI + bench (CMake, links libintono)
  app/                     Gradle Android app module + Kotlin (lifecycle, permission, JNI loader)
app/                       Flutter project (Dart UI, ffigen bindings, polling)
```

The Flutter app is the only UI. Kotlin is only the platform glue: runtime permission, route and focus events, starting and stopping the shim, and handing the engine pointer to Dart. **Nothing in Kotlin or Dart is on the audio path.**

### 2. Audio shim: C++ core with a thin Oboe layer

- `AudioPump` (portable C++, no Android headers): receives input blocks from a stream, calls `intono_process`, produces drone blocks with `intono_drone_render`, counts xruns and records per-callback timings. Because it has no Android dependency it is unit-tested on the host (Linux, ASan, TSan) with a fake stream, **tests first**. The Oboe layer is a few dozen lines that call it.
- Capture: Oboe input stream, `InputPreset::Unprocessed` (no AGC, noise suppression or echo cancellation), `PerformanceMode::LowLatency`, `SharingMode::Exclusive` with fallback to shared if the device refuses (the fallback and the granted mode are reported in the bench), `Usage`/`ContentType` for music, `Format::Float`, mono, `sampleRate` = the device's native rate (queried; `intono_config.sample_rate` is set from the opened stream, with `Unspecified` sample-rate conversion avoided), `framesPerDataCallback` set to the burst size.
- Drone: a separate Oboe output stream, `LowLatency`, exclusive with fallback, float, mono, the same sample rate, callback = `intono_drone_render`. Two streams, not duplex: Oboe has no single duplex object, and independent streams keep an output underrun from stalling capture.
- `libintono` is linked **statically** into the shim library (`libintono_android.so`), whose exported symbols are the `intono_*` C API (so Dart can `DynamicLibrary.open` it and ffigen sees the same header), the JNI entry points, and `intono_bench_*` (not part of the contract).
- Oboe comes from Google Maven as a Prefab package, version pinned in `android/app/build.gradle.kts` and recorded here when the shim PR lands (the exact version is verified on Google Maven in that PR, not assumed). New dependency, hence this ADR.
- Min SDK 24 (as for the existing Android jobs), `c++_static`, 16 KB page alignment (already checked by CI), ABIs arm64-v8a and armeabi-v7a (x86_64 only for the emulator).

### 3. Flutter, ffigen, polling

- Flutter stable, version pinned in `app/.flutter-version` (3.47 or newer stable at implementation time; the exact version and archive SHA-256 are recorded in the first Flutter PR).
- `dart:ffi` bindings generated by `package:ffigen` from `dsp/include/intono/intono.h` (generator script in `app/tool/`, output checked in, CI fails if regenerating changes it, so a header change without regenerated bindings cannot merge). ffigen needs `libclang-dev` on the CI runner.
- The UI polls on vsync: one `Ticker` calls `intono_read_frames` into a **preallocated** native buffer each frame and keeps only the newest frame for the meter (older frames are used only for history and are not displayed). `intono_read_notes` is polled at a lower rate (every ~100 ms). Reads happen on the Dart UI isolate, which satisfies "UI thread only". No platform channel messages per frame.
- Meter smoothing (needle) is done in Dart from the engine's display values; the DSP is not asked to smooth.

### 4. Live-meter screen

One screen: note name, cents (number), a needle, and a start/stop control; a drone selector and tonic come in a later PR, not this one. **Drone policy (Kelechi, 2026-11-23):** the drone is off by default and is only enabled automatically when headphones are connected (wired, USB or Bluetooth output, detected in Kotlin with `AudioManager` device callbacks and passed to `AudioPump::set_drone_enabled`). If the user turns it on while the output is the phone speaker, it plays and the screen shows a warning, "Use headphones for accurate results". Cancelling the drone's leak into the microphone (notch filtering) is Phase 3. The needle's range, colours and thresholds are display choices, not DSP gates. Permission denial and "microphone in use elsewhere" are shown as plain states.

### 5. Bench mode (on device)

A hidden screen (long-press on the version label) runs a fixed scenario and shows and exports a text report with **timings only, never audio**:

- **Worst hop and per-hop distribution**: `steady_clock` around `intono_process` per hop, per run, intrinsic = per-hop minimum over at least 10 runs (ADR 0008 method); median, p99, max; plus the callback-level worst.
- **Latency**: Oboe's measured input and output latency (`getTimestamp`-based where available, else the reported burst-based estimate, marked as estimate), and the engine note delay.
- **xruns**: `getXRunCount` on the output stream and an input-overrun count from the pump (callback gaps larger than 1.5 buffer periods).
- **With and without the denormal guard**: ADR 0008 Amendment 1 and `phase-2-plan.md` keep the guard on every platform; the bench compares by loading a second build of the shim with `INTONO_DENORMAL_GUARD=0` (a compile-time CMake option, default ON, only the bench APK ships the comparison library). This touches `filters.hpp`/`engine.cpp` behind that option; the default build's output stays bit-identical (G7 and the existing tests must pass unchanged), so it is not a DSP change in the sense of the freeze, and the information-only use was pre-authorised in `phase-2-plan.md`. If you read it differently, say so and the comparison drops out of Phase 2.
- Also: power cost of the 2 ms worker poll (Android battery stats exported by Kelechi, not collected by the app), the 30-minute soak (queue depth high-water, drops), and the intrinsic worst hop on the real phone, all feeding the ADR 0008 follow-ups in `phase-2-plan.md`.
- The bench input is the phone's real microphone for the latency and xrun numbers, and a built-in synthetic signal (a generated sine and a generated scale, no recordings) for the worst-hop numbers so runs are repeatable. Real clips are never bundled.

### 6. CI (no third-party actions)

- **Android shim**: host tests (`AudioPump`) in the existing `test` job matrix; an `android-app` job builds the Gradle app (debug APK) with the SDK, NDK and Gradle on the `ubuntu-24.04` image, uploads the APK. Gradle and Maven dependencies (Oboe, AGP, Kotlin) come from Google Maven and Maven Central, pinned by version.
- **Flutter**: an `app` job downloads the pinned Flutter archive from Google's official storage with the SHA-256 recorded in the repository and verified before use (no `flutter-action`). It runs `flutter analyze`, `flutter test` (Dart unit and widget tests, with a fake engine over the FFI interface), the ffigen freshness check, and `flutter build apk --debug`.
- The existing jobs are unchanged. New workflow file `.github/workflows/android-app.yml` so the DSP workflow's path filter and times stay as they are.
- The emulator cannot test capture, so audio-path correctness is tested on the host (`AudioPump`, with a fake stream and injected timing) and on the phone (bench mode and the live meter). The emulator job keeps testing `libintono` itself.

### 7. Delivery to the phone

CI uploads the debug APK as an artifact. Kelechi downloads it from the GitHub Actions run page (the workspace's proxy cannot fetch artifacts) and installs it with `adb install` or by opening it on the phone. The app id is the Flutter placeholder `com.example.intono` until Kelechi chooses the app name (standing rule: ask first); it is a single constant to change.

## PR sequence (each its own PR, tests first, CI green; PRs 1 to 3 touch no ADR decision once this ADR is merged and may be merged by Claude under the standing merge rule, PR 4 only if it changes no gate)

1. **Shim core**: failing host tests for `AudioPump` (block sizes, overrun/xrun accounting, drone path, timing stats, no allocation after start under the existing RT-safety harness), then the implementation. CMake target for the shim, no Oboe yet.
2. **Oboe streams + JNI + Gradle app + CI `android-app` job**: builds an APK; Kotlin permission and lifecycle; JNI start/stop; emulator-side smoke test of library load only.
3. **Flutter skeleton + ffigen + CI `app` job**: bindings, polling, fake-engine tests, still no UI beyond a debug text.
4. **Live meter screen** (note, cents, needle), widget tests.
5. **Bench mode** + the `INTONO_DENORMAL_GUARD` build option + the bit-identity CI job against `phase1-complete` + the report.
6. Phone measurements by Kelechi, recorded in an ADR amendment (device caps for the audio-thread worst hop, W3 and W4 on the phone). Milestone tag `phase2-android-complete` when these pass.

## Answers (Kelechi, 2026-11-23)

1. **Test phone (Kelechi, 2026-11-23):** Infinix Note 30, Android 14, mid-range MediaTek; the SoC is confirmed with `adb shell getprop ro.soc.model` in PR 6. A true low-end 2 GB device will be added before Phase 5, so the mid-range numbers are not the low-end numbers and ADR 0008's "low-end phone" measurement stays open until that device exists.
2. **Drone and headphones:** see the drone policy in decision 4 (default off unless headphones; speaker use allowed with a warning; notch filtering in Phase 3).
3. **App id:** the placeholder `com.example.intono` and a sideloaded debug APK are fine for Phase 2; the final app id is decided before Phase 5.
4. **Denormal-guard comparison option:** approved. `INTONO_DENORMAL_GUARD` (CMake option, default ON) is added in PR 5 **on the condition that CI proves the default build's output is bit-identical to `phase1-complete`**. The proof: a CI job builds the `phase1-complete` tag and the PR head with the default option and compares the output of `intono-cli` byte for byte (`tools/accuracy/diff_cli.py`) on the synthetic dev corpus (steady tones, scales, vibrato, noisy clips, silence-padded runs, inline and threaded); any difference fails the PR. The comparison library (guard off) ships only in the bench APK.

## Amendment 1 (2026-11-23, with PR 2): what the implementation fixed

Implementation details found while building PR 2. Decision 2's `c++_static` is the only change of substance.

- **Shared STL.** Oboe's Prefab package ships only `libc++_shared` builds, so `libintono_android.so` is built with `-DANDROID_STL=c++_shared` and the APK carries `libc++_shared.so`. This replaces `c++_static` in decision 2 for the Android app; the Phase 1 `libintono.so` job (static STL, no `libc++_shared`) is unchanged. Alternative not taken: building Oboe from source with the static STL (a second pinned source tree).
- **One Gradle module.** `android/app` is a single application module (`com.example.intono`) with the shim's CMake as its `externalNativeBuild`; a library module is split out only if the Flutter integration (PR 3) needs it.
- **Pins:** Gradle 8.14.3 (wrapper generated in CI, not committed), Android Gradle plugin 8.13.0, Kotlin 2.2.20, JDK 17, compileSdk and targetSdk 35, minSdk 24, build-tools 35.0.0, CMake 3.22.1, NDK 30.0.16248370, Oboe 1.9.3 (resolved from Google Maven in CI), JUnit 4.13.2, androidx.test runner 1.6.2 and ext-junit 1.2.1 (test only; `android.useAndroidX=true`).
- **Exports.** `libintono_android.so` exports exactly the eight `intono_*` functions and the JNI entry points (version script), is 16 KB aligned on all three ABIs, and CI fails otherwise. `liboboe.so` and `libc++_shared.so` are 16 KB aligned on the 64-bit ABIs; armeabi-v7a copies are 4 KB, which Play's 16 KB rule does not cover (64-bit only).
- **Streams.** Input: Oboe, `LowLatency`, `Exclusive` requested (the granted mode is reported by `info()`), float, mono, `InputPreset::Unprocessed`, native sample rate; the engine is created with the stream's rate. Output (drone): opened only while the drone plays, same rate, `LowLatency`, `Exclusive` requested, buffer 2 bursts.
- **CI.** `android-app` builds and unit-tests, then checks the APK; `android-app-emulator` runs an instrumented smoke test (library load, JNI, engine create/process/read/destroy on bionic). Capture itself is not testable on the CI emulator (`-no-audio`) and is first exercised on the phone.

## Note 1 (2026-11-23, with PR 3): Flutter's toolchain, and retiring the harness

Recorded as a note, not an amendment (Kelechi: within the ADR's intent, because Flutter dictates it).

- **Flutter host toolchain.** `app/android` builds with what Flutter 3.50.1 ships: Gradle 9.5.0, Android Gradle plugin 9.3.1, Kotlin 2.4.20 (Flutter's `android.newDsl=false` / `android.builtInKotlin=false` flags). NDK 30.0.16248370, CMake 3.22.1, Oboe 1.9.3, SDK levels and JDK 17 are the same as the harness; the shim sources, Kotlin glue and CMake are shared, not copied. The Flutter app's version pins therefore follow `app/.flutter-version`, not the Amendment 1 list, which applies to the harness.
- **Retiring the harness.** The harness app (`android/app`, its `MainActivity`, the `android-app` APK job and the harness Gradle toolchain) is removed once the Flutter app reaches parity with it (start/stop capture, drone with the headphone policy, stream facts), at the latest in PR 5, so only one Android toolchain remains. The shared Kotlin glue and the shim move under the Flutter host's tree when that happens; the unused harness `MainActivity` compiled into the Flutter APK goes with it. The instrumented smoke test and the shim host tests move with the shim.

## Note 2 (2026-11-23, after the first device run, with PR 5's first slice): what an input gap is

Decision 5 defined the input-overrun count as callback gaps larger than 1.5 buffer periods by the wall clock. On the Infinix Note 30 (shared mode, drone off) that gave about 10 per second, which is the signature of bursty shared-mode callbacks, not of lost audio. Superseded for the report:

- **Gap** = a discontinuity of the input stream's frames-read counter (AAudio frame position), logged with its time and size in frames. The pump tracks both plausible conventions of that counter (including or excluding the callback's own frames) and uses the one whose offset changes less; if the counter does not move, gaps are reported as unmeasured.
- Also reported, separately: the stream's own overrun count (polled every 16 callbacks), and the old wall-clock count renamed **late callbacks**. Whether any of the three matches audible loss is settled on the phone in PR 6.
- Slow hops (a chunk over 1 ms) are logged with their time, in CLOCK_MONOTONIC seconds like the app's UI-frame log, to attribute spikes (startup, GC, UI work). An arm64 profile APK is built in CI for timing runs.
- No gate, threshold or contract changes: `intono.h` and the DSP are untouched.

## Note 3 (2026-11-24, with PR 5's last part): the harness is retired

Carries out Note 1. The Flutter app has parity with the harness (start/stop capture, the drone with the headphone policy, the stream facts, now live) and more (meter, bench).

- **Removed:** the harness Gradle project (`android/settings.gradle.kts`, `build.gradle.kts`, `gradle.properties`, `android/app`), its `MainActivity`, the Gradle 8.14.3 / AGP 8.13.0 / Kotlin 2.2.20 pins of Amendment 1 (they applied to the harness only), and the `intono-harness-debug-apk` artifact. The only Android toolchain is the Flutter host's (Note 1).
- **Moved:** the Kotlin glue (`NativeAudio`, `DronePolicy`, `HeadphoneMonitor`), its JUnit test and the instrumented smoke test now live in `app/android/app/src` (`main`, `test`, `androidTest`). The Flutter app's debug APK is `intono-flutter-debug-apk`, the bench APK `intono-flutter-bench-apk`.
- **CI:** `android-app.yml` became `android-shim.yml` (host tests of the shim: AudioPump, bench core, comparison library; plain, ASan, TSan). The Gradle build, the Kotlin unit tests, the APK checks and the emulator smoke test run in `flutter-app.yml` (`app` and `android-emulator` jobs). The emulator job frees runner disk first, because Flutter, the SDK and the system image do not fit otherwise.
- **Deviation from Note 1 (accepted by Kelechi, 2026-11-27):** the C++ shim stays in `android/shim/` rather than moving under `app/android/`. With the Gradle project gone, `android/` holds only that portable C++ directory and no toolchain; its host tests (Linux, ASan, TSan) build it with plain CMake, independently of Gradle, so it is not part of the Flutter host's tree. `app/android` already references it, and moving it would change paths in two workflows, the CMake files and this ADR with no functional change. Revisit only if the iOS port needs a shared native location.

## Amendment 2 (2026-11-27, Kelechi's CI cost and speed request): how answer 4's bit-identity is proven

Answer 4's condition is unchanged: the default build's output must be byte-identical to `phase1-complete` on the synthetic dev corpus
(all phrase sets of seeds 21, 77, 123, 2024; each clip as is and with 3 s of digital silence; frames and notes; inline and threaded),
and any difference fails the PR. Only the mechanism changes, for speed: the job took 31 minutes, 30.5 of them in the threaded step,
because the CLI waits for the worker's 2 ms poll after every 128-sample chunk (ADR 0008), so 288 runs cost about their audio's length each.

- **Stored outputs, not a second build per PR.** `tools/accuracy/golden/phase1-complete.json` stores the SHA-256 of the tag's output for
  each of the 144 cases x 2 modes, and of each case's float32 input. It was made by `tools/accuracy/golden.py make` from the tag's binary
  (`e58070b`), which refuses to write a manifest unless the tag's inline and threaded outputs agree. `bit-identity-vs-phase1` now builds
  only the PR head and runs `golden.py check` inline and threaded.
- **Parallel runs.** The threaded runs are sleep-bound, so they run 32 at a time: about 45 s instead of 30.5 min (measured on a 2-core
  machine).
- **Provenance.** The `golden-provenance` job builds the tag itself and checks it against the manifest (inline and threaded) weekly, on
  manual runs, and on any change to the manifest, `golden.py`, `ref/synth.py` or `dsp.yml`. The manifest is only ever made from the tag.
- **Input drift is not a pass.** numpy, scipy and soundfile are pinned in CI to the versions recorded in the manifest. A changed input
  hash fails the job as `INPUT DRIFT` (the comparison is invalid), separately from `DIFF` (the output changed).
- A difference now reports which case and mode differ, not the first differing line; `diff_cli.py` against a build of the tag (unchanged,
  kept for that) shows the line.

## Consequences

- New dependencies: Oboe (Google Maven), Flutter SDK and pub packages (`ffi`, `ffigen`, plus the Flutter test SDK), Android Gradle plugin and Kotlin. All pinned, none involves user data.
- Verification of the Android app depends on CI and on the phone, not on the Claude workspace; the first PRs of each kind may need CI iteration.
- iOS repeats decisions 3 to 5 with Core Audio/AVAudioEngine instead of Oboe, in its own ADR.
- Nothing here changes `intono.h`, `openapi.yaml`, a gate, or a threshold.
