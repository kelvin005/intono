# ADR 0012: v1 is lean (no accounts, no backend, no sync; one-time Pro unlock); Phase 4 as written is not built

Status: **Proposed** (Kelechi's decision, 2026-11-27; this ADR records it and asks what replaces Phase 4). Needs Kelechi's "merge".

## Decision (Kelechi, 2026-11-27)

- **v1 has no accounts, no backend and no sync.** Practice data lives on the phone only (SQLite via drift, as the architecture doc says).
- **Pro is a one-time unlock** bought through **Google Play Billing** and **Apple's App Store in-app purchase** (a non-consumable
  product), not a subscription.
- **Phase 4 as written is not built for v1:** no Terraform staging, Go API, Firebase Auth, sync, RevenueCat webhooks, deletion worker,
  server observability or k6 load test.
- **No remote config:** values the doc puts in remote config (grade thresholds, coaching thresholds, paywall copy) are bundled with the
  app and change with a release (ADR 0011 answer 1).

```
v1 (this ADR)                                   architecture doc as written
phone: DSP · UI · drift DB · bundled config     phone ──sync──► Go API ── Postgres
store: one-time Pro unlock (Play / App Store)   Firebase Auth · RevenueCat · remote config · k6
no server, no account, nothing leaves the phone
```

## What in `docs/architecture.md` this makes outdated

| Section | Status for v1 |
|---|---|
| Overview ("the backend only stores ... accounts and subscriptions"), principle 3, system diagram's cloud half | no backend |
| Feature modules: Settings "remote config"; Scale grading and Coaching "thresholds in remote config" | bundled config |
| Monetisation hooks (subscription entitlements, 14-day grace, remote-configured paywall) | one-time unlock; the stores keep the purchase |
| Local data and sync: `outbox`, `entitlement_cache`, Sync protocol | not built; `sessions`, `note_stats`, `settings` stay |
| "Send a debug clip" (server upload) | not in v1 (no server) |
| Backend, Server data model, Capacity maths, Infrastructure regions, Scaling and reliability, Load testing | not built |
| App Store: "Accounts and subscriptions" | not applicable (no accounts; a non-consumable purchase with Restore) |
| Security: User rights (server-side deletion) | data is on the device only; deleting the app or "erase my data" in settings removes it |
| Observability, CI/CD: the server parts | not built; CI for the app and DSP unchanged |
| Build phases: Phase 4 (Backend) | not built; see the question below |

Everything else stands: on-device DSP, offline-first (the Phase 3 gate "all features work in airplane mode" is now simply true of the
whole app), the audio-thread rules, the privacy rules, the children rules, the C API.

A note at the top of `docs/architecture.md` points here; the outdated sections are kept as written for history, not edited.

## Consequences

- Nothing in the app needs the network. No server, no account, no personal data leaves the phone; the App Store privacy label and the
  Play data-safety form become "no data collected" if no crash or analytics SDK is added (question 3).
- A lost phone loses practice history unless the OS backup carries it (question 2).
- The standing rules about choosing an auth provider and an AWS region do not arise in v1.
- `openapi.yaml` (named as a contract in `CLAUDE.md`) does not exist on `main` and is not written for v1.

## Questions for Kelechi

1. **What replaces Phase 4?** Proposal: Phase 4 becomes **"Pro unlock and store readiness"**: the one-time purchase on both stores
   (with Restore), the Free/Pro split from the doc's feature table, the age gate if not done in Phase 3, the store listings' privacy
   answers. Gate: purchase, restore and offline use work on both stores' test tracks (Play internal testing; on iOS this waits for the
   TestFlight milestone and the Apple Developer Program, ADR 0010). Or fold it into Phase 5.
2. **OS backup of the practice database:** allow Android Auto Backup and iCloud device backup to include it (history survives a new
   phone, nothing goes to a server of ours), or exclude it?
3. **Crash reporting in v1:** none (Play Console vitals and Xcode Organizer only, recommended: no new vendor, simplest for under-13
   users), or a vendor SDK (its own ADR)?
4. **The billing plugin:** Flutter's own `in_app_purchase` package (flutter.dev, wraps Play Billing and StoreKit) is a new dependency;
   decided in the Phase 4 (or 5) ADR, not now.
